# Evaluation protocol and validity limits

Datasets are **SYNTHETIC BENCHMARK**, generated from owned NovaMart policy fiction and hand-authored task expectations. `evals/data/rag-v1.json` contains 30 questions with gold document/section, expected policy, difficulty and category. `agent-v1.json` contains 60 tasks across ten categories, each with customer/order/knowledge state, expected evidence/tools, allowed/forbidden actions and expected final outcome. Both are AI-reviewed; independent **human review is pending**. Do not call them real customer data.

The RAG baseline executes real BM25, ONNX embeddings and PostgreSQL vector distance. Recall@1/3/5, first relevant MRR, nDCG and separate no-answer abstention are recorded per case. The RAG ablation performs 36 configurations with actual temporary PostgreSQL indexes/vectors. Query memoization is cleared per case; model weights stay warm. “Answer success” is explicitly an evidence-coverage proxy, not generated response correctness. Exact raw scores and timings are saved JSON/CSV.

The agent ablation executes six configurations over all 60 tasks: Fake intent only; +retrieval; +business tools; +read verification; full +memory; router+specialist. It creates isolated real orders, products and inventory for each case and uses a labeled scripted test reviewer for eligible actions. A database regression verifies that a successful evaluation replacement does not change ordinary console stock. Default business lists exclude evaluation/test fixtures, including associated approval/refund/replacement rows; `include_evaluation=true` exposes them for inspection. This is real simulated-business execution, not a lookup of expected responses. Mandatory transactional approval and post-commit verification remain in all high-risk tool configurations; the verification ablation removes the optional read-response layer, not the safety invariant.

Metrics include task assertion success, golden evidence inclusion, golden tool-set inclusion, order-argument matching, narrow unsupported-success-claim detection, forbidden executed actions, escalation assertions, timing and actual provider usage (null for Fake). Inclusion scores are not precision. These assertions cannot detect every irrelevant answer, subtle hallucination or unauthorized policy exception. The sample is a development benchmark used during implementation, so generalization claims and statistical improvement claims are inappropriate.

Reproduce with `python -m evals.runner rag`, `python -m evals.rag_ablation`, `python -m evals.runner agent`, `python -m evals.gate evals/reports/agent-full.json`. The `llm_only` report actually fails the 0.80 gate; the full harness report passes. A prompt-specific HTTP gate also rejects mismatched versions. Real LLM evaluation remains NOT RUN until the operator configures and authorizes a provider.

Tests additionally cover transaction rollback, same-key and different-proposal concurrent refund attempts, replay after lost response, role denial, customer scoping, old-policy exclusion, malformed schema, injection data, provider retry/circuit, embedding timeout, MCP outage, cache failure, memory, SSE and actual TCP MCP parity. Browser tests verify the product flow; see [validation](validation.md) for exact run counts and outstanding remote CI status.
