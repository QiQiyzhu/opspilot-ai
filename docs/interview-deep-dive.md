# OpsPilot：从一个检索失败讲清业务权限

[完整案例](decision-case-study.md) · [逐条证据](../evals/reports/decision-case.json) · [核心实现](../backend/business.py)

## 30 秒版本

“我没有把检索命中当成可以自动退款。30 条模拟政策问题的真实 BGE 检索中，rerank 的 MRR 较高，但 4 条无答案只正确拒答 1 条；税务 return 甚至命中了退货政策。所以检索只提供审阅证据，执行仍必须通过当前政策、服务端角色、事务与独立验证。我用真实 PostgreSQL 展示待审零退款、越权 403、审批后重放只有一条账，以及等待期间资格过期后的 409。模型效果未测，审批是脚本 QA，业务是模拟的。”

## 3 分钟版本

**第一分钟：先承认失败。** 打开 `rag_29`，读问题、gold 无答案与返回段落，说明它不是语言模型幻觉测试，而是实际检索拒答失败。再切 `rag_02`：hybrid 第 1、rerank 第 4，解释为什么不能只按 MRR 选系统。原始 report 保留 120 行，不只挑成功例。

**第二分钟：展示一道真实边界。** 打开 `boundary_execution.steps`。同一套可执行政策下，检索命中与 31 天订单的 409 同时成立。合格订单的提案没有改业务状态，操作员也不能批准。审阅员执行后读取独立 verifier，核对批准金额 12900 分、记录/订单关联，而不是只读工具返回的“success”。同 key 重放只有 1 refund 与 1 audit。

**第三分钟：讲被拒方案和代价。** 分数阈值不能定义操作权限；第二个 Agent 也不能授予它。保留人工门槛带来等待，规则和文档需要版本管理，无答案文本仍可能不相关。下一步是新的近领域留出集与人工审阅，而不是调到四条无答案全过就宣布完成。真实 LLM、真实退款到账和生产吞吐没有执行证据。

## 被拒方案、反例和取舍

- **“MRR 高就自动执行”**：`rag_29` 的返回结果直接反驳；检索目标和授权目标不同。
- **“把 rerank 去掉就解决了”**：hybrid K3 较强，但 MRR 更低，无答案仍 1/4。没有一种模式在当前所有维度占优。
- **“只要版本没变，就信已批准快照”**：资格随时间变化；新增回归不修改 order.version 也应拒绝执行。
- **“全部交给第二个 Agent 审查”**：现有 Fake full 与 multi 同为 59/60，只能说明这套脚本下没有增益，不能得出真实多 Agent 无用；更不能替代权限控制。
- **“库存 verifier 比当前库存就够”**：其他订单会合法改库存。已有实现校验提案专属 movement 的数量与前后算术，限定在已提交预留证据。

## 五个追问

1. **为什么无答案不混进 Recall？** 无 gold 的问题没有相关段落排名；混入会掩盖拒答失败。因此 26 条计算 Recall/MRR，4 条单列拒答，数量太小不做显著性结论。
2. **词汇分数大于零为什么危险？** 当前 OR 过滤允许任何正词汇信号进入，即使语义很弱。调整需要新的近领域反例和误拒答权衡；这里没有声称已修好。
3. **审批开始后订单又变化怎么办？** 执行事务获取锁后重新读资格/版本/政策。取消还与审批共享 run 级线性化顺序；实际 barrier 测试验证两种顺序，不能仅检查 cancel 先结束的情况。
4. **数据库提交了，但用户没有收到响应怎么办？** 重放按幂等 key 返回已有提案，再独立验证；本演示观察到账本和审计各一条。持久任务调度和真实外部支付幂等仍是后续工作。
5. **你到底证明了什么？** 证明特定模拟订单的服务端防线真实生效、历史开发检索确有取舍。没有证明 LLM 推理效果、完整生产安全、真实结算或业务 ROI。
